# task-checklist 使用约定

本目录存放可执行的任务清单，一个 Markdown 对应一个任务主题。

## 记录约定

### 1. 用 GitHub 风格复选框记录任务

- 写法：`- [ ]` 表示未完成，`- [x]` 表示已完成
- 作用：让每个任务的完成状态在文件里直接可见，编辑器和 Git 平台都能渲染成勾选框
- 为什么：清单是执行状态的唯一事实来源；不依赖聊天记录或口头同步，任何人打开文件就能判断进度

### 2. 完成后打勾，不删除条目

- 写法：把 `- [ ]` 改成 `- [x]`，可在条目下补一行结果与日期
- 作用：保留已完成任务及其验收结果，形成可追溯的进度记录
- 为什么：直接删除会让「做过什么、是否验收通过」丢失，后来者容易重复劳动；打勾的成本远低于重新确认

### 3. 所有复选框都勾选后删除该 Markdown

- 写法：文件内不再有 `- [ ]` 时，直接删除该文件
- 作用：目录只保留仍有待办的清单，避免过期任务文件长期堆积
- 为什么：已完成的清单没有继续维护价值；删除不等于丢失，Git 历史仍可追溯，需要时可以从历史版本恢复

### 4. 文件名与文件头写清主题、范围和日期

- 写法：文件命名为 `<主题>.md`，头部写清范围、创建日期、待办数量
- 作用：让读者一眼识别清单对应的模块与当前进度
- 为什么：多个清单并存时，缺少范围和日期会导致误读、重复创建或把旧清单当成新任务

### 5. 只放可执行任务，每条写清作用与验收标准

- 写法：每条任务写清「作用 / 位置 / 做法 / 验收标准」；长篇背景放到 `docs/`
- 作用：让人一眼知道为什么要做、改哪里、做到什么程度算完成
- 为什么：只写“做什么”容易变成模糊待办；补上作用和验收，执行者才能判断优先级与完成边界

## 条目示例

```markdown
- [ ] P0-1 技能重名检测与确定性去重
  - 作用：避免同名技能在索引与 load_skill 之间指向不同正文
  - 位置：SkillRepository.skillsFor/find
  - 做法：按 name.toLowerCase() 检测冲突，保留入口路径排序第一条
  - 验收：同名技能只返回一条，日志能看出被跳过的目录
```
